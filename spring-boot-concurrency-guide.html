1. Основа конкурентности

Потоки и процессы

Процесс — это отдельный экземпляр программы со своим адресным пространством, памятью, файловыми дескрипторами и системными ресурсами. Когда мы запускаем Spring Boot приложение, обычно создается один Java-процесс JVM.

Поток — это путь выполнения внутри процесса. Все потоки одного процесса делят общую память heap, общие singleton-бины Spring, кэш, соединения и другие разделяемые объекты. Именно из-за общего доступа и возникают проблемы синхронизации.

В контексте Spring Boot
  • HTTP-запросы чаще всего обрабатываются потоками пула Tomcat/Jetty/Undertow.
  • @Async запускает работу в отдельном executor-пуле.
  • Планировщик @Scheduled использует свои потоки.
  • Kafka consumers, batch jobs, WebSocket handlers тоже используют конкурентное выполнение.
Что важно помнить
  • Spring singleton не означает "однопоточный".
  • Любой сервис может одновременно вызываться десятками запросов.
  • Статические поля и изменяемое состояние в бинах особенно опасны.
  • Проблемы часто проявляются только под нагрузкой, а не локально.

Типичный вопрос на практике: если у вас есть сервис корзины или счетчика просмотров, то каждый входящий HTTP-запрос может прийти на отдельном потоке. Значит, любой общий mutable state должен быть защищен или вынесен во внешнее хранилище.
1A. Отдельные runtime-пункты

Tomcat, Jetty, Undertow, @Async, @Scheduled, Kafka, batch, WebSocket

Tomcat / Jetty / Undertow

Это встроенные web-серверы Spring Boot. Они принимают HTTP-запросы и раздают их по рабочим потокам. На практике это значит: если одновременно пришло 100 запросов, они конкурируют за ограниченный thread pool сервера и за ресурсы приложения.

@Async

Аннотация для запуска метода в отдельном executor-пуле. Удобна для фоновых задач, уведомлений, интеграций и параллельных запросов, но требует явной настройки пула и понимания, что общий mutable state никуда не исчезает.

@Scheduled

Позволяет периодически запускать задачи по cron или fixed delay. Важно помнить, что планировщик тоже использует потоки, а значит задачи могут пересекаться по времени и создавать гонки за общие данные.

Kafka consumers

Консьюмеры читают сообщения параллельно по partition'ам и потокам listener-контейнера. Здесь часто всплывают race condition, повторная обработка, идемпотентность и борьба за доступ к БД или кэшу.

Batch jobs

Пакетные задачи обрабатывают большие объемы данных по расписанию или вручную. Если они идут параллельно с web-трафиком, нужно следить за конкуренцией за connection pool, CPU, память и блокировки в БД.

WebSocket handlers

Обработчики WebSocket работают с долгоживущими соединениями и событиями в реальном времени. Из-за большого числа одновременных сессий особенно опасно хранить небезопасное состояние в singleton-бинах или обычных коллекциях.

1B. Отдельные пункты по безопасности данных

Mutable state, synchronized, atomic, race condition, ExecutorService

Mutable state

Изменяемое состояние — это любые поля, коллекции и счетчики, которые можно менять после создания объекта. В Spring Boot это самый частый источник проблем, если такое состояние лежит в singleton-сервисе и доступно нескольким потокам.

synchronized

Нужен, когда важно не просто увидеть новое значение, а защитить целую критическую секцию: проверку, изменение и сохранение инварианта как одну неделимую операцию.

Atomic

Классы вроде AtomicInteger, AtomicLong и AtomicReference дают lock-free операции для простых сценариев: инкремента, compare-and-set, публикации ссылки. Это удобнее, чем synchronized, когда нужно защитить одну атомарную переменную, а не сложный блок логики.

Race condition

Гонка возникает, когда несколько потоков читают и меняют общие данные без согласованности. Итог зависит от порядка исполнения, который нельзя надежно предсказать, особенно под нагрузкой.

ExecutorService

Это базовый Java-механизм для управления пулом потоков и очередью задач. В Spring Boot его идея обычно живет через ThreadPoolTaskExecutor, но знать ExecutorService важно, потому что он объясняет, почему ручной new Thread() почти всегда хуже.

CompletableFuture

Это отдельный инструмент поверх executor'ов для композиции нескольких асинхронных шагов. Он особенно полезен, когда надо не просто "запустить фон", а собрать результат из нескольких параллельных источников.

2. Классические проблемы

Race condition и deadlock

Race condition возникает, когда итог зависит от непредсказуемого порядка выполнения потоков. Несколько потоков читают и меняют общее состояние без корректной координации.

public class InventoryService {
    private int stock = 10;

    public void reserve() {
        if (stock > 0) {
            stock--;
        }
    }
}

Здесь два потока могут одновременно увидеть stock > 0 и оба уменьшить значение. В результате инварианты ломаются: можно продать больше товаров, чем есть в наличии.

Как race condition проявляется в Spring Boot
  • Двойное списание денег при параллельной оплате.
  • Дублирование заказа при повторной отправке запроса.
  • Неконсистентный кэш в singleton-сервисе.
  • Повторная генерация одинакового номера документа.
Защита
  • synchronized, Lock, атомики, concurrent-коллекции.
  • Транзакции и блокировки на уровне БД.
  • Идемпотентность запросов.
  • Вынос критического состояния в внешнее хранилище.

Deadlock

Deadlock — это взаимная блокировка, когда поток A ждет ресурс, захваченный потоком B, а поток B одновременно ждет ресурс, захваченный потоком A. Никто не может продолжить выполнение.

private final Object lockA = new Object();
private final Object lockB = new Object();

public void method1() {
    synchronized (lockA) {
        synchronized (lockB) {
            // work
        }
    }
}

public void method2() {
    synchronized (lockB) {
        synchronized (lockA) {
            // work
        }
    }
}
Шаг 1
Поток T1 вошел в method1() и захватил lockA.
Шаг 2
Поток T2 вошел в method2() и захватил lockB.
Шаг 3
T1 ждет lockB, а T2 ждет lockA.
Итог
Оба потока зависли. Под нагрузкой это выглядит как "приложение перестало отвечать".
  • Всегда придерживайтесь единого порядка захвата локов.
  • Минимизируйте размер критической секции.
  • Избегайте вложенных блокировок без необходимости.
  • Для БД следите за порядком обновления таблиц и строк в транзакциях.
3. Запуск параллельной работы

Создание потока

В Java поток можно создать через Thread, Runnable, Callable и ExecutorService. Но в Spring Boot прямое создание потока через new Thread(...) почти всегда считается плохой практикой для бизнес-кода.

ПодходКогда использоватьКомментарий
new Thread()Почти никогда в Spring BootНет управления пулом, мониторинга, лимитов и graceful shutdown.
ExecutorServiceБазовая Java-конкурентностьЛучше, чем ручные потоки, но в Spring обычно удобнее объявить бин executor.
@AsyncАсинхронные сервисные операцииСтандартный путь для Spring Boot при корректной настройке пула.
CompletableFutureКомпозиция нескольких async-операцийХорош для fan-out/fan-in сценариев и объединения результатов.

Плохой пример

@Service
public class ReportService {
    public void buildReport() {
        new Thread(() -> heavyJob()).start();
    }
}

Лучше через управляемый executor

@Configuration
@EnableAsync
public class AsyncConfig {

    @Bean(name = "reportExecutor")
    public Executor reportExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(4);
        executor.setMaxPoolSize(8);
        executor.setQueueCapacity(100);
        executor.setThreadNamePrefix("report-");
        executor.initialize();
        return executor;
    }
}

@Service
public class ReportService {

    @Async("reportExecutor")
    public CompletableFuture<String> buildReport() {
        heavyJob();
        return CompletableFuture.completedFuture("done");
    }
}
Почему это лучше: пул потоков ограничивает конкуренцию, упрощает мониторинг, позволяет контролировать очередь, размер пула и выключение приложения.
4. Видимость и взаимное исключение

volatile и synchronized

volatile

volatile гарантирует видимость изменений переменной между потоками. Если один поток записал новое значение в volatile-поле, другие потоки увидят его без кэширования в устаревшем состоянии.

public class FeatureFlagHolder {
    private volatile boolean maintenanceMode;

    public boolean isMaintenanceMode() {
        return maintenanceMode;
    }

    public void setMaintenanceMode(boolean maintenanceMode) {
        this.maintenanceMode = maintenanceMode;
    }
}

Это хороший вариант для флага, сигнала остановки, режима конфигурации. Но volatile не делает составные операции атомарными.

private volatile int counter = 0;

public void increment() {
    counter++; // не атомарно: read - modify - write
}

synchronized

synchronized обеспечивает взаимное исключение: только один поток может зайти в критическую секцию на данном мониторе. Дополнительно он обеспечивает и корректную публикацию изменений памяти при входе и выходе из блока.

public class SequenceService {
    private int current = 0;

    public synchronized int next() {
        current++;
        return current;
    }
}
Когда подходит volatile
  • Флаг включения/выключения.
  • Признак завершения фоновой задачи.
  • Редко изменяемая ссылка на конфигурационный объект.
Когда нужен synchronized
  • Инкремент счетчика.
  • Проверка и изменение в одном блоке.
  • Защита нескольких связанных полей.
Свойствоvolatilesynchronized
Видимость измененийДаДа
Атомарность составной операцииНетДа
Блокировка других потоковНетДа
Типичный кейсФлаг состоянияКритическая секция
Spring Boot нюанс: если singleton-бин хранит mutable state, то недостаточно просто "добавить volatile почти везде". Нужно понять, требуется ли только видимость или именно защита последовательности операций.
5. Композиция асинхронных задач

CompletableFuture

CompletableFuture нужен, когда задача не просто запускается в фоне, а когда надо построить цепочку вычислений: получить данные из двух сервисов параллельно, объединить результаты, обработать ошибку и вернуть ответ клиенту.

Типовой сценарий

Пусть endpoint товара должен собрать карточку товара: базовую информацию из БД, цену из pricing-сервиса и остаток со склада. Эти три операции можно запустить параллельно, чтобы сократить latency.

@Service
public class ProductFacade {

    private final CatalogService catalogService;
    private final PricingService pricingService;
    private final StockService stockService;

    public CompletableFuture<ProductCardDto> loadProductCard(Long id) {
        CompletableFuture<ProductDto> productFuture =
                CompletableFuture.supplyAsync(() -> catalogService.load(id));

        CompletableFuture<PriceDto> priceFuture =
                CompletableFuture.supplyAsync(() -> pricingService.loadPrice(id));

        CompletableFuture<StockDto> stockFuture =
                CompletableFuture.supplyAsync(() -> stockService.loadStock(id));

        return CompletableFuture.allOf(productFuture, priceFuture, stockFuture)
                .thenApply(v -> new ProductCardDto(
                        productFuture.join(),
                        priceFuture.join(),
                        stockFuture.join()
                ));
    }
}
thenApply

Преобразует результат синхронной функцией.

thenCompose

Нужен, когда следующий шаг тоже возвращает CompletableFuture.

exceptionally

Позволяет задать fallback или преобразовать ошибку.

Что важно в Spring Boot

  • Не используйте по умолчанию общий ForkJoinPool.commonPool() для тяжелого I/O без причины.
  • Передавайте явный executor, если контролируете тип нагрузки.
  • Не делайте длинные цепочки без понятной обработки исключений и таймаутов.
  • Если асинхронность нужна только ради I/O в web-слое, иногда лучше смотреть в сторону reactive-стека.
return priceClient.loadPriceAsync(id)
        .orTimeout(2, TimeUnit.SECONDS)
        .exceptionally(ex -> PriceDto.unavailable())
        .thenCombine(stockClient.loadStockAsync(id),
                (price, stock) -> new OfferDto(price, stock));
Частая ошибка: запустить асинхронный код, а потом сразу вызвать join() в том же месте без выигрыша по времени. Тогда асинхронность превращается в усложненную синхронность.
6. Проверка под реальной нагрузкой

Нагрузочное тестирование

Нагрузочное тестирование показывает, как приложение ведет себя не на одном запросе, а на сотнях и тысячах. Для Spring Boot это способ проверить latency, throughput, устойчивость пула потоков, базы данных, кэша, внешних интеграций и лимитов.

Что измеряют
  • RPS или TPS.
  • Percentiles: p50, p95, p99.
  • Частоту ошибок.
  • Загрузку CPU, памяти, GC, thread pools, DB connections.
Популярные инструменты
  • JMeter.
  • k6.
  • Gatling.
  • wrk для быстрых HTTP-замеров.

Минимальный сценарий

1. Baseline
Снять метрики на 1 пользователе: среднее время ответа, SQL, логи, внешние вызовы.
2. Step load
Постепенно повышать количество виртуальных пользователей и смотреть, где начинается деградация.
3. Spike
Проверить, что будет при резком всплеске трафика.
4. Soak
Подержать сервис долго под нагрузкой и проверить утечки памяти, рост очередей и деградацию.

Что обычно ломается в Spring Boot

  • Слишком маленький или слишком большой пул потоков.
  • Блокирующие вызовы внутри @Async или web-обработчика.
  • Connection pool базы данных заканчивается раньше, чем HTTP thread pool.
  • Синхронизированные участки кода превращаются в бутылочное горлышко.
  • Логирование в очень больших объемах начинает само влиять на latency.
import http from 'k6/http';
import { sleep } from 'k6';

export const options = {
  vus: 50,
  duration: '30s',
};

export default function () {
  http.get('http://localhost:8080/api/products/42');
  sleep(1);
}
Идея: нагрузочный тест имеет смысл только вместе с метриками и логами. Если вы видите, что p95 вырос до 2 секунд, нужно еще понять, виноват ли CPU, пул БД, дедлок, внешнее API или rate limit.
6A. Инструмент отдельно

JMeter

JMeter — один из самых популярных инструментов для нагрузочного тестирования HTTP API, JDBC, JMS и других протоколов. Для Spring Boot его часто используют, когда нужно быстро собрать сценарий с авторизацией, набором endpoint'ов, параметрами запроса и отчетами по latency.

Когда JMeter удобен
  • Нужно быстро собрать сценарий через GUI.
  • Есть несколько шагов: логин, получение токена, вызов бизнес-методов.
  • Нужны отчеты по error rate, throughput, p95 и p99.
  • Команда уже использует .jmx сценарии в CI или вручную.
На что смотреть
  • Не только среднее время ответа, но и хвосты распределения.
  • Рост 4xx/5xx ошибок по мере увеличения нагрузки.
  • Насыщение thread pool, БД и внешних интеграций.
  • Поведение RateLimiter при превышении лимитов.
Практика: JMeter особенно полезен, если нужно показать, как приложение ведет себя при параллельных запросах к одному и тому же ресурсу. Это как раз хороший способ воспроизвести race condition в сервисах заказов, остатков или платежей.
7. Защита от перегрузки

RateLimiter

RateLimiter ограничивает частоту запросов. Его задача не только защищать от злоупотреблений, но и сохранять стабильность системы при пиках нагрузки.

Зачем ставят лимиты
  • Защита от brute-force и spam.
  • Стабилизация внешних API с ограниченной квотой.
  • Предотвращение перегрузки базы и downstream-сервисов.
  • Разделение честной пропускной способности между клиентами.
Где применяют
  • На API Gateway.
  • В контроллере или фильтре Spring Boot.
  • На вызовах внешних сервисов.
  • На критичных операциях: логин, оплата, отправка кода подтверждения.

Пример с Resilience4j

@Service
public class ExternalCatalogService {

    @RateLimiter(name = "catalogApi")
    public CatalogResponse fetchCatalog() {
        return client.load();
    }
}
resilience4j.ratelimiter:
  instances:
    catalogApi:
      limitForPeriod: 20
      limitRefreshPeriod: 1s
      timeoutDuration: 0

Здесь в каждом периоде длиной 1 секунда разрешено 20 вызовов. Если лимит исчерпан, лишние вызовы будут отклонены сразу.

Важно: локальный in-memory RateLimiter работает только внутри одного инстанса приложения. Если у вас несколько экземпляров сервиса, общий лимит часто реализуют через Redis или на уровне API Gateway / ingress.
ПодходПлюсМинус
Локальный limiter в сервисеПросто добавитьНе глобален между инстансами
Gateway / Nginx / API managementЕдиная точка контроляМеньше бизнес-контекста
Redis-based limiterГлобальный лимитСложнее инфраструктурно
8. Диагностика и наблюдаемость

ELK стек

ELK обычно означает Elasticsearch + Logstash + Kibana. Иногда вместо Logstash используют Fluent Bit или Filebeat, но идея остается той же: собрать логи из Spring Boot, централизованно сохранить, индексировать и удобно искать.

Elasticsearch

Хранит и индексирует логи, чтобы можно было быстро выполнять поиск и агрегации.

Logstash / Beats

Собирает, преобразует и пересылает логи из приложений и серверов.

Kibana

Дает интерфейс для поиска по логам, dashboards и расследования инцидентов.

Зачем это Spring Boot приложению

  • Искать ошибки по traceId или requestId между несколькими сервисами.
  • Понимать, какие endpoint'ы чаще всего падают под нагрузкой.
  • Связывать пики 429/500 ошибок с конкретным временем и клиентами.
  • Смотреть stacktrace централизованно, а не на каждом сервере отдельно.

Практический подход

{
  "timestamp": "2026-04-05T12:00:00Z",
  "level": "INFO",
  "service": "video-games-shop",
  "thread": "http-nio-8080-exec-7",
  "traceId": "7ca4d8dce92d4d81",
  "path": "/api/orders",
  "message": "Order created",
  "userId": 42
}

Самый полезный формат для машинного анализа — структурированные JSON-логи. Тогда Kibana может фильтровать по полям: traceId, path, level, thread, userId.

Что логировать обязательно
  • Время и уровень.
  • Имя сервиса и окружение.
  • traceId / correlationId.
  • HTTP method, path, статус, latency.
  • Ошибку и ключевые бизнес-идентификаторы.
Чего избегать
  • Паролей, токенов, номеров карт, персональных данных.
  • Слишком шумных логов на горячем пути.
  • Неструктурированных многострочных сообщений без контекста.
  • Логирования "всего подряд" вместо полезных событий.
Связь с нагрузочным тестированием: во время load test вы можете в Kibana видеть, с какого момента пошли таймауты, всплеск ошибок 429, очереди в executor'ах или зависшие операции. ELK дает не только хранение логов, но и возможность расследовать причины деградации.
9. Цельная картина

Как связать все темы в одном Spring Boot проекте

Представим интернет-магазин игр. Пользователь открывает карточку товара, оформляет заказ и вызывает внешние сервисы оплаты, каталога и рекомендаций. Тогда темы из этого конспекта складываются в одну практическую картину:

Потоки
HTTP-запросы приходят в thread pool веб-сервера. Несколько пользователей работают одновременно.
Race condition
Без синхронизации можно дважды списать остаток товара или сгенерировать одинаковый номер заказа.
Deadlock
Некорректные блокировки в Java-коде или транзакциях БД могут подвесить оформление заказа.
volatile / synchronized
Нужны для корректной работы разделяемого состояния, флагов и критических секций.
CompletableFuture
Помогает параллельно подтянуть цену, остатки и рекомендации, чтобы сократить время ответа.
Load testing
Показывает, выдержит ли приложение 100, 500 или 1000 пользователей одновременно.
RateLimiter
Не дает одному клиенту или всплеску трафика положить сервис логина, оплат или внешнюю интеграцию.
ELK
Позволяет понять, где именно система начала тормозить, выбрасывать ошибки или застревать.
Если нужно коротко сформулировать на собеседовании: "Spring Boot приложение почти всегда многопоточное, поэтому я должен понимать видимость памяти, синхронизацию, безопасную асинхронность, поведение под нагрузкой и инструменты диагностики в production".
Итог

Самая полезная стратегия в backend-разработке: не рассматривать эти темы по отдельности. Потоки влияют на корректность данных, корректность данных влияет на поведение под нагрузкой, нагрузка выявляет узкие места, а ELK и метрики помогают объяснить, почему система деградировала. Именно вместе эти знания делают Spring Boot сервис предсказуемым и устойчивым.
