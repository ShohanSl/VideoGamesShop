Java: подробные ответы по основным темам

Ниже собраны развернутые ответы по темам, которые часто встречаются на учебе, экзаменах и собеседованиях: bulk-операции, Stream API и лямбды, Optional, пирамида тестирования, TDD, unit- и интеграционные тесты, а также инструменты JUnit и Mockito.

Bulk операции

Что такое bulk operations

Bulk operations, или пакетные операции, это операции, которые применяются сразу к набору элементов, а не к одному объекту. Идея в том, что мы описываем действие над целой коллекцией данных: отобрать, преобразовать, отсортировать, удалить, обновить или агрегировать все элементы сразу.

В Java bulk-операции чаще всего ассоциируются с работой с коллекциями и Stream API. Вместо ручного цикла for, где разработчик сам управляет обходом, проверкой условий и сборкой результата, можно описать задачу на более высоком уровне: например, взять список игр, оставить только дорогие, преобразовать в названия и отсортировать по алфавиту.

Зачем они нужны

  • Делают код короче и легче для чтения.
  • Позволяют сосредоточиться на логике, а не на механике обхода коллекции.
  • Лучше выражают намерение: видно, что код делает, а не только как именно это делает.
  • В некоторых случаях позволяют эффективнее использовать оптимизации, в том числе параллельную обработку.

Где встречаются

  • В коллекциях Java при фильтрации, сортировке, группировке, преобразовании.
  • В базах данных при массовом обновлении или удалении записей.
  • В ORM и JPA при batch insert или batch update.
  • В обработке файлов, логов, событий и больших наборов данных.
List<String> result = games.stream()
    .filter(game -> game.getPrice() > 40)
    .map(Game::getTitle)
    .sorted()
    .toList();

Здесь одна цепочка действий обрабатывает сразу весь список игр. Это и есть пример bulk-подхода: работа не с одной игрой, а с коллекцией как с единым потоком данных.

Stream API и лямбды

Что такое Stream API

Stream API появился в Java 8 и стал важной частью современного стиля разработки. Stream позволяет обрабатывать последовательность элементов декларативно: мы не пишем, как именно перемещаться от элемента к элементу, а описываем цепочку операций над потоком данных.

Важно понимать, что Stream сам по себе не хранит данные. Он лишь предоставляет способ пройтись по источнику данных, например по списку, множеству, массиву или даже по результатам чтения файла.

Как строится обработка в Stream API

Обычно работа со stream выглядит как цепочка из трех частей: источник данных, одна или несколько промежуточных операций и одна терминальная операция. Источником может быть коллекция, массив, генератор значений или файл. Промежуточные операции подготавливают и трансформируют поток, а терминальная операция завершает вычисление и дает итоговый результат.

Типы операций в Stream API

  • Промежуточные: filter, map, sorted, distinct, limit. Они возвращают новый stream.
  • Терминальные: toList(), collect(), count(), forEach(), findFirst(). Они завершают обработку.

Промежуточные операции являются ленивыми. Это значит, что они не выполняются сразу в момент написания цепочки. Реальная обработка начинается только тогда, когда вызывается терминальная операция. Благодаря этому Stream API может работать эффективнее и выстраивать обработку как единый конвейер.

Что такое лямбды

Лямбда-выражение это короткая запись анонимной функции. Оно позволяет передавать поведение в метод без создания отдельного класса. Например, выражение x -> x * 2 означает: взять значение x и вернуть его, умноженное на 2.

Лямбды особенно хорошо работают вместе с функциональными интерфейсами, то есть интерфейсами, у которых только один абстрактный метод. Например: Predicate, Function, Consumer, Supplier.

Пример обработки коллекции

List<String> titles = games.stream()
    .filter(game -> game.getPrice() > 30)
    .map(Game::getTitle)
    .sorted()
    .toList();

Разбор примера:

  • stream() создает поток из коллекции.
  • filter(...) оставляет только игры дороже 30.
  • map(...) преобразует объекты Game в строки с названиями.
  • sorted() сортирует названия.
  • toList() собирает результат в список.

Подробно об основных операциях Stream API

Ниже перечислены самые важные операции, которые чаще всего используются на практике. Их удобно знать не только по названию, но и по назначению.

  • filter(predicate) — оставляет только те элементы, которые удовлетворяют условию. Например, можно выбрать только активных пользователей или только дорогие товары.
  • map(function) — преобразует каждый элемент в другой объект. Например, из объекта Game можно получить только название, цену или DTO.
  • flatMap(function) — используется, когда один элемент нужно превратить в поток из нескольких элементов, а затем "расплющить" все в один общий поток. Частый пример: из списка заказов получить единый поток всех товаров из этих заказов.
  • sorted() — сортирует элементы по естественному порядку. Для строк это алфавитный порядок, для чисел — по возрастанию.
  • sorted(comparator) — сортирует по собственному правилу, например по цене, по длине строки или по дате создания.
  • distinct() — удаляет дубликаты. Работает на основе equals() и hashCode().
  • limit(n) — берет только первые n элементов. Полезно для пагинации или отбора нескольких первых результатов.
  • skip(n) — пропускает первые n элементов. Часто используется вместе с limit.
  • peek(consumer) — позволяет посмотреть на элементы в процессе обработки. Обычно применяется для отладки, а не для основной бизнес-логики.
  • forEach(consumer) — выполняет действие для каждого элемента и завершает поток. Это терминальная операция.
  • collect(...) — одна из самых важных терминальных операций. Позволяет собрать результат в список, множество, карту или более сложную структуру.
  • toList() — упрощенный способ получить список из потока.
  • count() — возвращает количество элементов после всех фильтраций и преобразований.
  • findFirst() — возвращает первый элемент в виде Optional.
  • findAny() — возвращает некоторый элемент, особенно полезен в параллельных stream.
  • anyMatch(predicate) — проверяет, есть ли хотя бы один элемент, удовлетворяющий условию.
  • allMatch(predicate) — проверяет, удовлетворяют ли условию все элементы.
  • noneMatch(predicate) — проверяет, что ни один элемент не соответствует условию.
  • min(comparator) и max(comparator) — находят минимальный или максимальный элемент.
  • reduce(...) — сворачивает поток в одно итоговое значение, например сумму, произведение или объединенную строку.

Примеры разных операций

long expensiveCount = games.stream()
    .filter(game -> game.getPrice() > 50)
    .count();

Optional<Game> firstGame = games.stream()
    .filter(Game::isActive)
    .findFirst();

int totalPrice = games.stream()
    .map(Game::getPrice)
    .reduce(0, Integer::sum);

collect и Collectors

Операция collect особенно важна, потому что она позволяет собирать результат не только в список, но и в более сложные структуры. Обычно вместе с ней используют класс Collectors.

  • Collectors.toList() — собрать элементы в список.
  • Collectors.toSet() — собрать элементы во множество.
  • Collectors.toMap(keyMapper, valueMapper) — собрать данные в карту.
  • Collectors.groupingBy(...) — сгруппировать элементы по признаку.
  • Collectors.joining(...) — объединить строки в одну.
  • Collectors.counting(), summingInt(...), averagingDouble(...) — агрегирующие операции.
Map<String, List<Game>> byGenre = games.stream()
    .collect(Collectors.groupingBy(Game::getGenre));

String joinedTitles = games.stream()
    .map(Game::getTitle)
    .collect(Collectors.joining(", "));

Промежуточные и терминальные операции

Это одно из ключевых различий в Stream API. Промежуточные операции возвращают новый stream и позволяют продолжать цепочку. Терминальные завершают работу и выдают конечный результат.

Промежуточные

filter, map, flatMap, sorted, distinct, limit, skip.

Терминальные

toList, collect, count, findFirst, forEach, reduce, min, max.

Важные особенности Stream API

  • Один stream нельзя использовать повторно после терминальной операции.
  • Потоки удобны для обработки данных, но не всегда подходят для сложной пошаговой логики с множеством побочных эффектов.
  • Лучше избегать изменения внешнего состояния внутри stream-операций.
  • Параллельные потоки parallelStream() стоит применять осторожно, потому что они не всегда дают выигрыш и могут усложнить поведение программы.

Плюсы и ограничения

  • Плюс: код компактный и хорошо читается для типовых операций над данными.
  • Плюс: легко строить цепочки обработки.
  • Плюс: можно использовать метод-ссылки, например Game::getTitle.
  • Минус: слишком сложные stream-цепочки могут быть трудны для отладки и чтения.
  • Минус: не всегда потоковая запись лучше обычного цикла, особенно если логика ветвится и становится громоздкой.
Optional

Что такое Optional и зачем он нужен

Optional<T> это контейнер, который явно показывает, что значение может присутствовать, а может отсутствовать. Он был введен, чтобы сделать работу с отсутствующими значениями более безопасной и выразительной по сравнению с прямым возвратом null.

Когда метод возвращает просто объект, разработчик может забыть, что там потенциально может быть null. Когда метод возвращает Optional, это сигнал: нужно явно обработать случай отсутствия значения.

Где Optional особенно полезен

  • В методах поиска: пользователь найден или не найден.
  • В репозиториях: запись по ID есть или ее нет.
  • В вычислениях, где результат может отсутствовать по бизнес-логике.

Основные методы

  • Optional.of(value) создает Optional для гарантированно не-null значения.
  • Optional.ofNullable(value) создает Optional даже если значение может быть null.
  • isPresent() проверяет наличие значения.
  • orElse(defaultValue) возвращает значение или значение по умолчанию.
  • orElseThrow(...) выбрасывает исключение, если значение отсутствует.
  • map(...) позволяет преобразовать содержимое Optional.
String name = Optional.ofNullable(user)
    .map(User::getName)
    .orElse("Гость");

В этом примере, если объект user равен null, результатом будет строка "Гость". Если пользователь есть, то берется его имя.

Когда Optional не стоит использовать

  • Как поле JPA-сущности, потому что это часто неудобно и не соответствует типичному стилю ORM.
  • Как параметр метода без явной необходимости.
  • В местах, где обычная проверка на null проще и понятнее.

Идея Optional не в том, чтобы полностью запретить null, а в том, чтобы сделать потенциальное отсутствие значения явной частью контракта метода.

Пирамида тестирования и TDD

Пирамида тестирования

Пирамида тестирования это модель, которая подсказывает, как разумно распределять тесты в проекте. В основании пирамиды находится большое количество unit-тестов, выше располагается меньшее количество интеграционных тестов, а на вершине находится небольшое число end-to-end тестов.

Основание

Unit-тесты проверяют небольшие куски логики изолированно. Они быстрые, дешевые и запускаются часто.

Середина

Интеграционные тесты проверяют взаимодействие компонентов, например сервиса с репозиторием и базой данных.

Вершина

E2E-тесты проверяют систему почти как пользователь. Они самые медленные и дорогие в поддержке.

Почему именно пирамида

  • Unit-тесты дешевле писать и запускать, поэтому их должно быть больше.
  • Интеграционные тесты нужны, но они медленнее и сложнее.
  • E2E-тесты полезны, однако из-за своей стоимости их должно быть немного.

Если в проекте слишком много UI- или E2E-тестов и мало unit-тестов, то проверки становятся медленными, нестабильными и дорогими. Пирамида нужна как ориентир на баланс.

TDD

TDD, или Test Driven Development, это подход, при котором разработка начинается с теста. Сначала пишется тест на требуемое поведение, затем пишется минимальный код, чтобы этот тест прошел, после чего выполняется рефакторинг без изменения поведения.

Цикл TDD

  • Red — написать тест, который пока не проходит.
  • Green — написать минимальный код, чтобы тест стал зеленым.
  • Refactor — улучшить код, сохранив рабочие тесты.

Что дает TDD

  • Помогает сначала продумать поведение и требования.
  • Снижает риск написания лишнего кода.
  • Обычно улучшает дизайн API, потому что код создается с точки зрения использования.
  • Дает быстрый набор регрессионных тестов.

При этом TDD требует дисциплины и не всегда применяется буквально во всех частях проекта. Но как подход к проектированию логики через тесты он очень полезен.

Unit vs интеграционные тесты

Разница между unit- и интеграционными тестами

Unit-тесты и интеграционные тесты решают разные задачи, и их нельзя считать взаимозаменяемыми. Unit-тест отвечает на вопрос: правильно ли работает конкретная единица логики в изоляции. Интеграционный тест отвечает на вопрос: правильно ли несколько компонентов работают вместе.

Unit-тест

Проверяет один класс, один метод или одну небольшую бизнес-операцию отдельно от внешнего мира.

Интеграционный тест

Проверяет взаимодействие нескольких частей системы: например, контроллера, сервиса, репозитория и БД.

Особенности unit-тестов

  • Быстро запускаются.
  • Обычно не требуют поднятия Spring-контекста, базы данных или сети.
  • Хорошо локализуют проблему: если тест упал, понятно, в какой логике ошибка.
  • Часто используют моки и стабы для зависимостей.

Особенности интеграционных тестов

  • Работают медленнее, потому что поднимают больше инфраструктуры.
  • Лучше обнаруживают проблемы конфигурации, биндинга, SQL, транзакций и интеграции слоев.
  • Сложнее в поддержке, но ближе к реальному поведению приложения.

Пример

Если мы тестируем метод сервиса и подменяем репозиторий через Mockito, это unit-тест. Если мы поднимаем Spring-контекст и проверяем, что сервис действительно работает с настоящим репозиторием и тестовой БД, это интеграционный тест.

На практике хороший проект использует оба типа. Unit-тесты дают скорость и точность, а интеграционные тесты подтверждают, что система реально собирается в рабочее целое.

JUnit и Mockito

JUnit

JUnit это основной фреймворк для написания тестов в Java. С его помощью создаются тестовые методы, организуются проверки, запускаются сценарии и формируется структура тестового набора.

  • @Test помечает тестовый метод.
  • @BeforeEach выполняется перед каждым тестом.
  • @AfterEach выполняется после каждого теста.
  • Assertions, например assertEquals, assertTrue, assertThrows, проверяют результат.

Mockito

Mockito это библиотека для создания mock-объектов. Mock нужен тогда, когда мы не хотим использовать реальную зависимость в тесте. Например, если сервис зависит от репозитория, можно не подключать настоящую базу данных, а просто подменить репозиторий заглушкой с нужным поведением.

Что позволяет Mockito

  • Настроить поведение зависимости через when(...).thenReturn(...).
  • Проверить, был ли вызван нужный метод через verify(...).
  • Изолировать тестируемый класс от базы данных, HTTP-клиентов, внешних сервисов и других зависимостей.
@Test
void shouldReturnGame() {
    when(gameRepository.findById(1L)).thenReturn(Optional.of(game));

    Game result = gameService.getById(1L);

    assertEquals("Witcher 3", result.getTitle());
    verify(gameRepository).findById(1L);
}

В этом примере JUnit запускает тест и проверяет результат, а Mockito подменяет поведение репозитория. Такой тест быстрый, потому что не требует настоящей базы данных.

JUnit и Mockito вместе

Обычно JUnit отвечает за структуру и запуск тестов, а Mockito за изоляцию зависимостей. В связке они очень удобны для unit-тестирования сервисов, валидаторов, мапперов и других компонентов бизнес-логики.
